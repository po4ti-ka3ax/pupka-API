### Как происходит деплой
1. Изменения — только через Pull Request: CI + ревью
2. Merge в main → CI: test → deploy (Render deploy hook, ref = SHA) → smoke
3. React собирается Vercel из main автоматически
4. Авария: Rollback на Render, затем git revert через PR

## Лабораторная 11 — ответы

- **helmet, CORS только для:** 
  Использование `helmet` для защиты HTTP-заголовков (скрытие отпечатков сервера, защита от XSS и clickjacking). CORS настроен строго на разрешённый фронтенд-домен (`http://localhost:5173` и production-домен на Vercel/Render), чтобы запретить несанкционированные кросс-доменные запросы.

- **Rate limit:** 
  Ограничение запросов подключено через `express-rate-limit`. Для эндпоинтов авторизации (`/api/auth/login` и `/register`) настроен лимит **10 попыток / 15 минут** для защиты от брутфорса и DDoS-атак.

- **Валидация zod для:** 
  Входных данных пользователей при регистрации и входе (`registerSchema`, `loginSchema`), а также при создании и обновлении товаров (`productSchema`, `productUpdateSchema`) с проверкой типов, длины строк, положительных значений цен и обязательных полей.


## Лабораторная 11 — ответы

- **Таблица аудита «до / после»:**

| Уязвимость / Параметр | До hardening (до защиты) | После hardening (после защиты) |
| :--- | :--- | :--- |
| **Защита заголовков** | Отсутствовала (нет Helmet) | Заголовки безопасности активированы |
| **Ограничение запросов** | Лимиты на auth-роутах отсутствовали | Введен Rate Limit (10 запросов / 15 минут) |
| **Валидация данных** | Ручная проверка / частичная | Строгая схема через Zod с защитой от лишних полей |
| **Mass Assignment** | Поле `role` можно было передать при регистрации | Поле `role` жестко изолировано на бэкенде |

- **npm audit:**
  - **Что нашли:** Уязвимости умеренной и низкой степени критичности в старых версиях транзитивных зависимостей.
  - **Что исправили:** Обновили пакеты до безопасных версий с помощью `npm audit fix`.
  - **Что оставили и почему:** Незначительные предупреждения в dev-зависимостях, которые не влияют на production-сборку.

- **Были ли секреты в истории git:** 
  Нет, секретные данные (токены, пароли БД, `JWT_SECRET`) хранились исключительно в локальных файлах `.env` и `.env.test`, которые добавлены в `.gitignore` и не попадали в репозиторий.

- **Был ли возможен mass assignment (role: admin) до валидации:** 
  Да, при сохранении в базу нефильтрованного объекта `req.body` злоумышленник мог передать при регистрации поле `role: "admin"` и получить права администратора. После внедрения Zod-схем лишние поля отсекаются.

- **Зачем trust proxy на Render:** 
  Платформа Render работает за обратным прокси (load balancer). Без включения `app.set('trust proxy', 1)` Express определяет IP-адрес клиента как IP самого прокси, из-за чего `express-rate-limit` блокировал бы всех пользователей сразу, а не по их реальному IP.

- **Почему проверки в React-форме недостаточно:** 
  Валидация на стороне фронтенда (в React) служит только для удобства пользователя в интерфейсе. Её легко обойти, отправив прямой HTTP-запрос через Postman или cURL, поэтому строгая проверка на сервере через Zod обязательна.

- **Время отката на Vercel:** 
  Откат занимает **~15 секунд** (переключение на предыдущий стабильный деплой). 
  **Почему после отката нужен git revert:** Откат на Vercel меняет только текущую версию на хостинге, но не меняет историю Git. Без `git revert` следующий коммит снова подтянет сломанный код из ветки при автодеплое.

- **Использовал(а) ли ИИ и для чего:** 
  ИИ использовался как технический ассистент для настройки схем Zod, рефакторинга middleware, отладки интеграционных тестов (Vitest/Supertest) и диагностики сетевых/конфигурационных ошибок.
